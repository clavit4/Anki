# CLAUDE.md — internal project notes (not part of the site, do not link from index.html)

This file is for a future Claude session picking this repo back up cold. It is
technical, dense, and written for a model to parse, not for a human reader —
if you're a human and this reads like ai slop, that's because it partly is:
large chunks were generated by Claude across many iterative sessions and kept
terse on purpose. It is deliberately **not** referenced anywhere in
`index.html`/`style.css`/`js/*` and GitHub Pages never serves it as part of
the app (nothing fetches it, nothing links to it) — it only exists for
whoever/whatever opens this repo in an editor or a fresh Claude Code session.
See also the "Not published" section at the bottom for why it stays that way
even under GitHub Pages' default Jekyll behavior.

## What this project is

A personal, single-user Japanese-kanji flashcard app — an Anki clone, much
smaller in scope. Static site, no backend, no build step, no framework.
Deployed via GitHub Pages at `clavit4.github.io/Anki/`. Repo:
`clavit4/Anki`. The owner (git author / GitHub account context: xpaauli) uses
it personally to drill kanji recognition and readings; iterated on almost
entirely through casual, typo-prone chat requests to Claude across many
sessions rather than written specs — expect terse, direct feedback and fast
iteration norms rather than long design discussions in future sessions too.

## Hard architectural constraint: one global scope, no bundler

There is no module system, no bundler, no `import`/`export`, no build step.
`index.html` loads 14 plain classic `<script>` tags in a fixed order:

```
js/01-config.js
js/02-csv.js
js/03-storage.js
js/04-state.js
js/05-modal.js
js/06-deck-list.js
js/07-card-editor.js
js/08-count-screen.js
js/09-quiz-core.js
js/10-quiz-flashcard.js
js/11-quiz-multichoice.js
js/12-results.js
js/13-activity-heatmap.js
js/14-boot.js
```

All 13 files share **one single global scope**, exactly as if they were
concatenated into one `app.js` (that's literally how this started — the
whole app was one file before it was split for readability, purely by
feature area, and the load order above is what makes it work: a file can
only reference a `const`/`function` defined in a file loaded *before* it).
Consequences that matter for future edits:

- **Never** declare the same top-level `const`/`let`/`function` name in two
  files — there's no per-file namespace, so that's a `SyntaxError`
  (`Identifier 'x' has already been declared`) at parse time, not a runtime
  surprise. When splitting/moving code, diff the identifier sets between old
  and new locations to catch this before it ships.
- A file can freely call a function or read a value defined in an
  *earlier*-loaded file (e.g. anything in `09-quiz-core.js` can use `state`
  from `04-state.js`), but never the reverse.
- `index.html` has a single shared cache-busting query string appended to
  every `<script src="...?v=N">` and to `style.css?v=N`. **Bump N whenever
  any JS or CSS file changes** — GitHub Pages / browsers will otherwise
  serve a stale cached copy indefinitely, since there's no build hash.
  Check the current N with `grep -n '?v=' index.html` before bumping (all
  script tags share one N; bump them together, not per-file).
- No TypeScript, no JSX, no npm dependencies at all. `'use strict';` is the
  first line of every file — keep that convention on any new file.

## The `state` object (`js/04-state.js`)

```js
state = {
  decks: {},              // deckId -> { cards: [...] } | { error: true, cards: [] }
  activeDeck: null,       // the deck config object currently selected (has .id/.name)
  sessionCards: [],       // the cards in the CURRENT quiz session, fixed order for the session
  index: 0,               // position within sessionCards
  correct: 0,             // count of GOT_IT grades this session
  missed: [],             // cards graded MISSED this session, for the results "To review" list
  flipped: false,         // flashcard-mode flip state
  quizMode: 'flashcard',  // 'flashcard' | 'multichoice' — controls which renderer 09-quiz-core dispatches to
  previewSort: 'original',// current filter/sort mode, one of SORT_MODES (01-config.js)
  previewVisibleCards: [],// the PLAYABLE pool under the current filter — see "play pool" below
  history: [],            // stack of { index, grade } per graded card this session, for Undo
}
```

Card shape (from CSV or a custom deck): `{ front, back, id, activeDefault }`.
A CSV row with no id column doesn't stay `null` — `csvToCards()`
(`02-csv.js`) auto-numbers it in file order via `assignMissingIds()`
(collision-avoiding against any explicit ids elsewhere in the same file),
same idea as `nextCardId()` in `03-storage.js` for a manually-added card.
Exact duplicate rows (same front AND back) are silently dropped there too,
keeping the first. `id` staying `null` past that point would only happen
for a card that reaches `state` through some other path entirely — see
`cardStorageKey`/`cardActiveKey` in `03-storage.js` for the content-hash
fallback key scheme (`recall:<deckId>:temp:<hash>`) that exists for that
case, though nothing in the app currently produces it.

## localStorage key scheme

Everything lives under a `recall:` prefix so `deleteDeckStorage(deckId)` can
sweep a whole deck's data (cards + history + overrides) in one pass by
prefix match:

- `recall:<deckId>:card:<id>` — append-only array of `{ grade, timestamp }`,
  never trimmed. `cardScore()` averages only the last `HISTORY_WINDOW` (7)
  entries — a rolling average, not the all-time average. This is
  deliberate, not a bug, if it comes up again.
- `recall:<deckId>:active:<id>` — `'1'`/`'0'`, only written when it
  *overrides* the CSV's own default (a toggle back to the CSV default
  deletes the key rather than storing a redundant value).
- `recall:<deckId>:cards` — a custom (user-uploaded) deck's full parsed
  card array, JSON.
- `recall:customDecks` — registry array of `{ id, name }` for every
  uploaded deck; `id` is `custom:<slugified-name>` (deterministic, so
  re-uploading a CSV under the same name updates the same deck instead of
  duplicating it).

`decks/confusable-kanji.json` is a static asset fetched over HTTP (like a
deck CSV), **not** localStorage — it's shared/global data, not per-device
state.

## Play pool vs. list membership (important, easy to get wrong again)

The deck-preview filter (`state.previewSort`) controls two related but
distinct things that must **not** be conflated:

1. The **list** rendered in `#previewList` — every card matching the
   filter, including inactive (skipped) ones, shown dimmed. This lets you
   find and re-enable a skipped card while looking at e.g. "Weaker".
2. The **play pool** (`state.previewVisibleCards`), which the count-grid
   buttons (10/25/50/100/All) draw sessions from — this must exclude
   inactive cards, so toggling a card off actually keeps it out of study,
   regardless of which filter you're looking at.

The one deliberate exception: the `nonactive` filter's whole *purpose* is
drilling exactly your skipped cards, so for that one filter the play pool
is **not** further restricted to active cards (it would otherwise always be
empty). See `renderDeckPreview()` in `08-count-screen.js` for the branch
that applies this exception.

The count-grid (`renderCountGrid`) sizes its buttons off
`state.previewVisibleCards.length` (the current filter's pool, not the
deck's total card count) and disables (grays out, never hides) any button
whose count exceeds the pool — this keeps the grid's layout stable across
filter switches instead of buttons appearing/disappearing.

## Multiple choice mode specifics

- Deliberately does **not** call `recordGrade`/`removeLastGradeRecord` — a
  multiple-choice attempt never touches a card's persistent grade history,
  so it can't skew the Weakest/Strongest sort or the score-stripe color in
  flashcard mode. This is intentional isolation between the two modes, not
  an oversight.
- The prompt shows `card.back` truncated at its first `[` character
  (`mcPromptText`) — decks encode readings as `"meaning [on X, kun Y]"`,
  and showing the bracket part would give away the answer via furigana
  recognition instead of testing meaning recall.
- Distractors come from `CONFUSABLE_KANJI_GROUPS`
  (`decks/confusable-kanji.json`, a plain array of arrays of visually/
  structurally similar kanji, hand-curated by the user — e.g. `["問","間","聞"]`).
  `buildMultipleChoiceOptions` shuffles the correct card's group, takes up
  to 3 members that also exist elsewhere in the *same deck*, and pads with
  random other cards' fronts if the group is too small/empty/missing. Groups
  with more than 4 members correctly rotate through different combinations
  across repeated draws (not just the first 3 in file order) because the
  group is shuffled before slicing.
- Answer feedback is intentionally asymmetric: a **correct** answer flashes
  green and auto-advances after `CORRECT_ADVANCE_DELAY` (300ms) with no tap
  required; a **wrong** answer locks the options, reveals the correct one in
  green and the picked one in red, and waits for a tap anywhere on
  `.mc-stage` before advancing (`pendingMcGrade` + the stage's click
  listener) — deliberately not auto-advanced, so there's time to actually
  read which one was right.
- Locking answered options uses `.is-locked` (`pointer-events: none`), **not**
  the `disabled` attribute — a `disabled` button never dispatches `click` at
  all, which would swallow taps instead of letting them bubble up to
  `.mc-stage`'s "tap anywhere to continue" listener.
- **Known-fixed footgun, don't reintroduce it**: `.mc-option:hover` in
  `style.css` must stay wrapped in `@media (hover: hover)`. Without that
  guard, iOS Safari's "tap leaves a sticky `:hover` at that screen position
  until the next tap elsewhere" behavior made the just-answered option's
  green/mint hover tint appear to "leak" onto the next question's button in
  the same grid slot (a fresh, unrelated element, just rendered at the same
  coordinates) — this reads to a user as "the highlight never goes away."
  Confirmed via Playwright with a real touch-emulated context
  (`devices['iPhone 13']`, checked `matchMedia('(hover: hover)').matches`
  is `false`) that gating on `(hover: hover)` removes the effect entirely on
  touch, while leaving normal desktop-mouse hover intact.

## Theme (CSS custom properties, `style.css` `:root`)

Dark theme, deliberately **not** near-black/terminal-black and **not**
saturated neon-green ("Matrix" was an explicit rejected direction) — settled
on a charcoal background (`--bg: #12191b`) with a soft pastel mint accent
(`--mint: #7ad9c4`). A separate `--correct`/`--correct-strong`/
`--correct-glow` (true saturated green, `#3ecf6d`) exists specifically for
multiple-choice "this is the right answer" feedback, kept visually distinct
from the ambient `--mint` branding color used everywhere else in the chrome
— don't collapse these two greens back into one token, that was a deliberate
split. Rose/amber/lime tokens plus `--correct` map to the four grades
(Missed/Hard/Almost/Got it) and drive `SCORE_COLOR_STOPS` in
`03-storage.js` for the continuous (not bucketed) score-stripe gradient in
the deck preview — if you retune one, retune the other to match, they're
meant to look like the same palette. Pink/rose as a primary *accent* (not
just the Missed-grade color) was explicitly tried and rejected earlier in
this project's history; don't reintroduce a pink accent without the user
asking again.

Also note the `[hidden]` attribute vs. author CSS `display` gotcha that's
bitten this project more than once: an author-origin rule (even at equal
specificity) always beats the UA stylesheet's `[hidden] { display: none }`.
Any selector that both needs a non-`none` `display` (e.g. `display: flex`
for a modal or a stage) *and* needs to be toggled via the `hidden` attribute
needs an explicit `.selector[hidden] { display: none; }` override — see
`.modal-overlay[hidden]`, `.card-stage[hidden]`, `.mc-stage[hidden]` for the
existing pattern to copy if a new hideable-flex-container shows up.

## Study/session flow at a glance

1. Deck list (`screen-deck`) → tap a deck → `openCountScreen(deck)`
   (`08-count-screen.js`) sets `state.activeDeck`, renders the mode toggle,
   count grid, and card-preview list, shows `screen-count`.
2. Pick Flashcards or Multiple choice (`state.quizMode`), optionally cycle
   a filter (`state.previewSort`, via the sort-toggle button), then tap a
   count button → `startSession(n)` (`09-quiz-core.js`) slices `n` cards
   from `state.previewVisibleCards`, resets session state, shows
   `screen-quiz`.
3. Per card, `renderCurrentCard()` dispatches to
   `renderFlashcardCard`/`renderMultipleChoiceCard` based on `quizMode`.
   Grading (`gradeCard`/`answerMultipleChoice` → `recordGradeAndAdvance`)
   writes to `state.history`, advances `state.index`, and calls
   `finishSession()` once the session is exhausted.
4. `finishSession()` (`12-results.js`) shows `screen-results` with the
   score, the missed-cards list, and a single "Back to deck" button that
   calls `openCountScreen(state.activeDeck)` — this returns to the *same
   deck's* count/preview screen, not the deck list, and does not restart a
   session. (Earlier versions had two buttons, "Study again"/"Choose
   another deck" — removed per explicit user request; don't add them back
   without being asked.)
5. "End session" mid-quiz (`#quitQuiz`) goes straight to results if
   anything was graded (`state.history.length > 0`), otherwise back to
   `screen-count` directly — quitting before grading a single card has
   nothing to show a results screen *for*.

## Testing convention used throughout this project's history

No test framework, no CI. Verification has consistently been: run
`python3 -m http.server` from the repo root, then drive the page with
Playwright (`chromium.launch({ executablePath: '/opt/pw-browsers/chromium-*/chrome-linux/chrome' })`
in this environment) from a throwaway script in the scratchpad directory —
click through the actual flow, read back computed styles/classList/`state`
via `page.evaluate`, and screenshot when a visual claim needs confirming
(e.g. the touch-hover-leak investigation used a real
`devices['iPhone 13']` emulated context specifically because the bug was
hover-capability-dependent and a default desktop-mouse context couldn't
disprove or confirm the fix). Keep using this pattern — write a small
disposable script per investigation rather than a persisted test suite,
since there's no build/CI pipeline consuming one.

## Git/deploy convention

- Feature work happens on a branch (naming has varied by session, e.g.
  `claude/anki-ui-refinements-...`), merged into `main` with `--no-ff` once
  verified, then pushed. `main` is what GitHub Pages actually serves.
- Bump the shared `?v=N` cache-buster in `index.html` in the *same commit*
  as any JS/CSS change — forgetting this means the live site can silently
  keep serving a stale file after deploy.
- No package.json, no lockfile, nothing to install — cloning the repo and
  opening `index.html` (or serving the directory statically) is the entire
  setup.

## Not published

GitHub Pages, by default (repo has no `_config.yml` and no explicit
"disable Jekyll" setting otherwise), runs Jekyll over the repo and *would*
auto-render a top-level Markdown file into an HTML page reachable by URL
even with nothing linking to it. A `.nojekyll` file was added at the repo
root alongside this file specifically so that doesn't happen — it disables
Jekyll processing entirely, so this file (and any other future `.md`) is
just an inert text file in the repo, never compiled into a served page.
If `.nojekyll` ever goes missing, put it back before adding more Markdown
here.
